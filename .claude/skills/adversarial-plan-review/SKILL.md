# 敵対的レビュー（修正方針の提案時）

## 原則

修正方針はユーザーに出す前に、**その方針を潰しにかかるレビュアーの立場**で検証する。
レビューは「実コードで確かめた事実」に基づく。想像だけの懸念は「未検証」と明記する。
目的は方針を良くすることで、指摘の数を稼ぐことではない。根拠のない指摘や水増しはしない。

## 手順

1. **方針の下書き** — 何を、どのファイルで、どう変えるかを決める。
2. **前提の洗い出し** — 方針が暗黙に依存している前提を列挙する（「この参照は他から使われていない」「このメソッドは Start より後に呼ばれる」など）。
3. **前提を実コードで検証** — Grep / Read で呼び出し元・参照元・Prefab/シーン YAML・ScriptableObject アセットを確認する。確認できたものには `file:line` を添える。
4. **攻撃観点で叩く** — 下の観点表を全部見る。該当なしの観点は報告しなくてよい。
5. **深刻度で分類** — 致命（壊れる・データ消失）／重要（回帰・保守性悪化）／軽微（好み・将来の懸念）。
6. **方針を修正** — 致命・重要は方針に反映するか、採用しない理由を書く。
7. **出力フォーマットで提示**。

## 攻撃観点

### 汎用
- 根本原因を直しているか、症状を隠しているだけか
- もっと単純な代替案はないか（変更ファイル数・新クラス数を減らせないか）
- スコープ外の変更が混ざっていないか
- 既存の呼び出し元・派生クラスを壊さないか（Grep で全参照を確認したか）
- 元に戻しやすいか、段階的に入れられるか
- どうやって動作確認するか（CLI ビルド・自動テストがないので、Editor での確認手順が具体的に書けるか）

### Unity / このプロジェクト固有
- **ライフサイクル**: Awake / OnEnable / Start の順序依存、シングルトン初期化前のアクセス、`OnDestroy` での購読解除漏れ
- **破棄済みオブジェクト**: Unity の `== null` と `?.` / `is null` の違い。タワーのアップグレード・合成（`FusionManager.TryFuse`）で GameObject が破棄された後も参照を持ち続ける箇所がないか
- **Time.timeScale = 0**: 一時停止中のコルーチン（`WaitForSeconds` vs `WaitForSecondsRealtime`）、DOTween の `SetUpdate`、UI 操作
- **シリアライズ**: フィールド名・型・クラス名の変更で Inspector 参照や Prefab/シーンの値が消えないか（`FormerlySerializedAs`、`.meta` の GUID）
- **ScriptableObject**: 実行時に `TowerStats` / `EnemyData` / `LevelAsset` などを書き換えて共有状態を汚していないか
- **シーン遷移**: シングルトン（`GameManager`, `FusionManager`, `TowerActionPanel` など）や static 状態がシーン再読込・ステージセレクト導入時に破綻しないか
- **交戦状態**: `IsEngaged` / `DisengageDefender()` / Guardian のリスポーンなど、片側だけ状態が残るケース
- **飛行敵・攻撃属性**: `canAttackFlying`、`AttackType` と耐性の扱いが変更で漏れないか
- **プロジェクトルール**: null チェック時の `Debug.LogError` / `Debug.LogWarning` 必須ルール、`*.ai.md` や `Docs/design/` の設計との整合

## 出力フォーマット

```
## 修正方針（初案）
<箇条書きで簡潔に>

## 敵対的レビュー
| # | 指摘 | 深刻度 | 根拠 | 対応 |
|---|------|--------|------|------|
| 1 | ... | 致命/重要/軽微 | `path:line` で確認 / 未検証 | 方針に反映 / 不採用（理由） |

## 修正後の方針
<レビューを反映した最終案。初案から変わった点を明示>

## 残るリスク・未検証事項
<Editor での確認が必要なこと、コードだけでは判断できないこと>
```

重大な指摘が出なかった場合も表は省略せず、「確認した観点と結果」を書いた上で「致命・重要な指摘なし」と明記する。

## よくある逃げ道

| 言い訳 | 実際 |
|--------|------|
| 「小さい修正だからレビュー不要」 | 小さい修正ほど参照元確認を省いて壊す。規模に応じて短くしてよいが省略はしない |
| 「ユーザーが急いでいる」 | 表 1 つ分の手間。省略しない |
| 「たぶん他からは使われていない」 | Grep して `file:line` で示す。できないなら「未検証」と書く |
| 「懸念を並べておけば十分」 | 指摘ごとに対応（反映 / 不採用理由）を決める。投げっぱなしにしない |
| 「指摘が少ないと手抜きに見える」 | 水増ししない。確認した観点を示せば十分 |
